# 我是面试官 - 系统概要设计文档

## 1. 系统概述

### 1.1 项目背景

"我是面试官"是一款基于大语言模型（LLM）的智能面试助手数字员工，旨在帮助面试官高效地进行技术面试。系统通过AI分析候选人简历与岗位HC（Headcount）要求，自动生成梯度化的面试问题清单，并在面试后根据面试官的评分给出综合评价与职级推荐。

### 1.2 系统目标

- **智能化**：利用大模型自动分析简历与岗位要求，生成针对性面试问题
- **梯度化**：按难度分级规划问题，支持初级/中级/高级/专家等级判定
- **标准化**：提供统一的评分体系与职级评定标准
- **高效化**：减少面试官准备工作量，提升面试效率与质量
- **多工种覆盖**：支持技术、产品、设计、数据等多岗位类型的面试场景

### 1.3 支持的工种类型

| 工种分类 | 工种名称    | 代码             | 核心考察维度                    |
| ---- | ------- | -------------- | ------------------------- |
| 技术研发 | 前端开发工程师 | frontend\_dev  | HTML/CSS/JS、框架原理、工程化、性能优化 |
| 技术研发 | 后端开发工程师 | backend\_dev   | 编程语言、数据库、系统设计、微服务         |
| 技术研发 | 算法工程师   | algorithm\_eng | 机器学习、深度学习、模型优化、业务落地       |
| 技术研发 | 测试工程师   | test\_eng      | 测试理论、自动化测试、性能测试、质量保障      |
| 技术研发 | 数据开发工程师 | data\_dev      | SQL、数据仓库、ETL、大数据组件        |
| 产品设计 | 产品经理    | product\_mgr   | 需求分析、产品设计、数据分析、项目管理       |
| 产品设计 | UI设计师   | ui\_designer   | 设计理论、工具技能、用户体验、设计系统       |

### 1.4 核心价值

- 降低面试准备成本
- 统一面试评价标准
- 提供客观的职级评定依据
- 沉淀面试题库与评价数据
- 跨工种标准化面试流程

### 2.2 技术架构选型

本系统借鉴 OpenClaw 的本地优先（Local-first）架构理念，采用**轻量级分层架构**，去除不必要的 Gateway、Docker 沙箱、Agent 执行引擎等重型组件，保留核心设计思想：插件化、Markdown 存储、工作空间隔离。

#### 2.2.1 技术栈选型

| 层级          | 技术选型                     | 版本要求  | 说明                        |
| ----------- | ------------------------ | ----- | ------------------------- |
| 前端          | React 18 + TypeScript    | ≥ 5.0 | 用户界面层，组件化开发               |
| UI 框架       | Ant Design / TailwindCSS | 最新    | 组件库/样式框架                  |
| 工具层         | Node.js + TypeScript     | ≥ 20  | 文件操作、AI 调用、数据处理           |
| 状态管理        | Zustand / Redux Toolkit  | 最新    | 轻量级状态管理                   |
| Markdown 解析 | gray-matter + remark     | 最新    | YAML Front Matter + MD 解析 |
| AI 引擎       | OpenAI API / 通义千问        | -     | 大语言模型接口                   |
| 文件操作        | fs/promises (Node.js 内置) | -     | 异步文件系统操作                  |
| 构建工具        | Vite                     | ≥ 5.0 | 前端构建与开发服务器                |
| 包管理         | pnpm                     | ≥ 8.0 | 依赖管理                      |

#### 2.2.2 与 OpenClaw 架构对比

| OpenClaw 组件     | 是否采用   | 原因            | 替代方案                          |
| --------------- | ------ | ------------- | ----------------------------- |
| 微核架构            | ✅ 借鉴   | 核心+扩展的设计思想    | 插件化 Prompt 模板系统               |
| 本地优先            | ✅ 完全采用 | 数据隐私、离线可用     | Markdown 文件存储                 |
| 工作空间            | ✅ 完全采用 | 工种隔离、独立配置     | `workspaces/{job_role}/` 目录结构 |
| Skills 插件系统     | ✅ 适配采用 | 工种差异化扩展       | 工种插件（Prompt+规则+模板）            |
| Gateway 控制平面    | ❌ 不采用  | 无需多平台消息路由     | 直接本地文件操作                      |
| Docker 沙箱       | ❌ 不采用  | 无代码执行需求       | 无                             |
| PiAgent 运行时     | ❌ 不采用  | 无需 ReAct 推理循环 | 直接调用 LLM API                  |
| sqlite-vec 向量存储 | ⚠️ 可选  | 题库语义搜索        | 简单关键词搜索或后期引入                  |

#### 2.2.3 架构特点

- **本地优先**：所有数据存储在本地 Markdown 文件，无需数据库
- **TypeScript 全栈**：前后端统一语言，降低维护成本
- **插件化扩展**：工种配置、Prompt 模板、评分规则均可插件化
- **轻量级设计**：去除重型组件，聚焦面试辅助核心功能
- **工作空间隔离**：每个工种独立目录，数据互不干扰

### 2.4 架构设计理念

借鉴 OpenClaw 的核心设计思想，本系统采用以下架构原则：

#### 2.4.1 本地优先（Local-first）

- **数据主权**：所有数据存储在用户本地文件系统，不依赖云端数据库
- **离线可用**：核心功能无需联网即可使用（AI 生成环节除外）
- **数据隐私**：简历、面试记录等敏感信息完全本地化
- **可移植性**：工作空间目录可直接复制、备份、版本控制

```
┌─────────────────────────────────────────────────────────────┐
│                     本地优先架构                               │
│                                                               │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐      │
│  │  前端 UI    │───▶│  工具层     │───▶│  文件系统   │      │
│  │  (React)    │◀───│  (Node.js)  │◀───│  (Markdown) │      │
│  └─────────────┘    └──────┬──────┘    └─────────────┘      │
│                            │                                │
│                            ▼                                │
│                     ┌─────────────┐                         │
│                     │  AI 服务    │ (仅生成环节需要联网)       │
│                     │  (LLM API)  │                         │
│                     └─────────────┘                         │
└─────────────────────────────────────────────────────────────┘
```

#### 2.4.2 微核 + 扩展

- **微核**：核心功能仅包含文件读写、Markdown 解析、AI 调用
- **扩展点**：工种插件、Prompt 模板、评分规则、报告模板均可扩展
- **解耦设计**：核心逻辑与工种逻辑分离，新增工种无需修改核心代码

```
┌─────────────────────────────────────────────────────────────┐
│                      微核 + 扩展架构                          │

│  ┌─────────────────────────────────────────────────────┐    │

│  │  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌────────┐ │    │

│  │  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌────────┐ │    │
```

#### 2.5.3 插件加载机制

```typescript
// 插件加载器伪代码
interface InterviewPlugin {
  plugin_id: string;
  name: string;
  prompts: PromptTemplates;
  rules: GradingRules;
  templates: ReportTemplates;
}

class PluginManager {
  private plugins: Map<string, InterviewPlugin> = new Map();
  
  // 加载插件
  async loadPlugin(pluginPath: string): Promise<void> {
    const meta = await readJSON(`${pluginPath}/plugin.json`);
    const prompts = await loadPrompts(`${pluginPath}/prompts`);
    const rules = await loadRules(`${pluginPath}/rules`);
    const templates = await loadTemplates(`${pluginPath}/templates`);
    
    this.plugins.set(meta.plugin_id, {
      plugin_id: meta.plugin_id,
      name: meta.name,
      prompts,
      rules,
      templates
    });
  }
  
  // 获取工种插件
  getPlugin(jobRole: string): InterviewPlugin {
    return this.plugins.get(jobRole);
  }
}
```

### 5.4 文件操作规范

#### 5.4.1 读取操作

- 使用 Node.js `fs/promises` 模块异步读取文件内容
- 使用 `gray-matter` 解析 YAML Front Matter 获取元数据
- 使用 `remark` 解析 Markdown 内容获取正文

```typescript
import fs from 'fs/promises';
import matter from 'gray-matter';

// 读取 Markdown 文件并解析元数据
async function readMarkdownFile(filePath: string) {
  const content = await fs.readFile(filePath, 'utf-8');
  const { data, content: body } = matter(content);
  return { metadata: data, body };
}
```

#### 5.4.2 写入操作

- 新文件创建时自动生成唯一 ID（使用 `crypto.randomUUID()`）
- 更新文件时保留原有 Front Matter 字段
- 使用临时文件 + 重命名的方式实现原子写入，避免文件损坏

```typescript
import path from 'path';

// 原子写入：先写入临时文件，再重命名
async function atomicWrite(filePath: string, content: string) {
  const tempPath = `${filePath}.tmp`;
  await fs.writeFile(tempPath, content, 'utf-8');
  await fs.rename(tempPath, filePath);
}
```

#### 5.4.3 查询操作

- 使用 `fs.readdir()` 按目录结构遍历文件
- 读取 Front Matter 字段进行过滤匹配
- 支持关键词全文搜索（简单字符串匹配或后期引入全文检索库）

```typescript
// 遍历工作空间下的所有面试记录
async function listInterviews(workspacePath: string) {
  const interviewsDir = path.join(workspacePath, 'interviews');
  const entries = await fs.readdir(interviewsDir, { withFileTypes: true });
  return entries
    .filter(e => e.isDirectory())
    .map(e => e.name);
}
```

### 5.5 数据一致性保障

- 使用文件锁防止并发写入冲突
- 重要操作前备份原文件
- 定期校验文件完整性
- 提供数据恢复机制

## 6. AI Prompt设计

### 6.1 简历解析Prompt

```
请分析以下简历内容，提取以下信息：
1. 基本信息（姓名、联系方式）
2. 教育背景（学校、专业、学历、时间）
3. 工作经历（公司、职位、时间、主要职责）
4. 技术技能（编程语言、框架、工具）
5. 项目经验（项目名称、技术栈、个人贡献）

请以JSON格式返回结构化数据。
```

### 6.2 问题生成Prompt

```
基于以下候选人简历和岗位需求，生成一份面试问题清单：

【工种类型】
{job_role} (如：前端开发工程师/后端开发工程师/产品经理等)

【候选人信息】
{candidate_info}

【岗位需求】
{hc_requirement}

【考察维度及权重】
{evaluation_dimensions}

要求：
1. 生成{question_count}道面试问题
2. 按难度分为5个等级（L1基础-L5专家）
3. 每个等级至少2道题
4. 问题需覆盖该工种的核心考察维度
5. 问题类型覆盖：基础知识、实战应用、系统设计、软技能
6. 每道题附带期望答案要点和评分参考
7. 问题需结合候选人简历中的经历和技能

请以JSON格式返回。
```

### 6.3 等级评定Prompt

```
根据以下面试评分记录，给出综合评价：

【评分明细】
{score_records}

【职级标准】
P3: 初级入门，L1通过率≥60%
P4: 初级熟练，L1≥80%, L2≥50%
P5: 中级，L2≥70%, L3≥40%
P6: 高级，L3≥60%, L4≥40%
P7: 专家，L4≥60%, L5≥40%

请给出：
1. 综合评分（0-100）
2. 推荐职级
3. 优势分析
4. 不足分析
5. 综合评价总结
```

## 7. 职级评定体系

### 7.1 职级定义

| 职级 | 名称     | 能力描述           | 工作年限参考 |
| -- | ------ | -------------- | ------ |
| P3 | 初级（入门） | 能在指导下完成基础开发任务  | 0-1年   |
| P4 | 初级（熟练） | 能独立完成常规开发任务    | 1-3年   |
| P5 | 中级     | 能负责模块设计，解决复杂问题 | 3-5年   |
| P6 | 高级     | 能主导系统设计，技术选型   | 5-8年   |
| P7 | 专家     | 技术领域专家，能解决疑难问题 | 8年以上   |

### 7.2 评分权重

| 难度等级 | 权重  | 说明               |
| ---- | --- | ---------------- |
| L1   | 10% | 基础题，区分是否具备基础知识   |
| L2   | 20% | 理解题，区分是否能应用知识    |
| L3   | 30% | 分析题，区分是否具备解决问题能力 |
| L4   | 25% | 设计题，区分是否具备架构能力   |
| L5   | 15% | 专家题，区分技术深度       |

### 7.3 综合评分计算公式

```
综合评分 = Σ(各题得分 × 题目权重 × 考察维度权重) / Σ(权重) × 10

等级判定逻辑：
1. 计算各难度等级通过率
2. 计算各考察维度得分
3. 对照职级标准表
4. 取满足条件的最高职级
```

### 7.4 工种差异化评定

不同工种在评定时侧重点不同，系统根据工种配置自动调整评定策略：

| 工种      | 评定侧重点       | 加分项           |
| ------- | ----------- | ------------- |
| 前端开发工程师 | 框架深度、性能优化能力 | 开源贡献、工程化实践    |
| 后端开发工程师 | 系统设计、高并发处理  | 架构经验、技术选型能力   |
| 算法工程师   | 理论基础、模型效果   | 论文发表、比赛成绩     |
| 测试工程师   | 质量意识、自动化能力  | 测试平台建设、质量体系建设 |
| 数据开发工程师 | 数据建模、SQL优化  | 大数据组件深度、数据治理  |
| 产品经理    | 产品思维、数据分析   | 成功产品案例、商业洞察   |
| UI设计师   | 用户体验、设计系统   | 设计影响力、作品集质量   |

## 8. 非功能性需求

### 8.1 性能要求

- 简历解析响应时间：< 5秒
- 问题生成响应时间：< 15秒
- 报告生成响应时间：< 5秒
- 文件读取响应时间：< 100ms（单文件）
- 工作空间加载时间：< 1s（含元数据解析）
- 前端首屏加载时间：< 2s

### 8.2 安全要求

- 简历文件本地存储，不上传第三方服务（AI 调用时仅发送必要文本）
- 敏感信息（联系方式等）可选择性脱敏展示
- AI 调用使用 API Key 环境变量管理，不硬编码
- 操作日志记录到本地日志文件

### 8.3 本地优先架构要求

- **离线可用**：核心功能（查看简历、浏览题库、查看报告）无需联网
- **数据主权**：所有数据存储在用户本地，用户拥有完全控制权
- **版本控制友好**：工作空间目录可直接纳入 Git 管理
- **可移植性**：工作空间可通过压缩包完整迁移
- **备份机制**：支持手动导出工作空间，支持自动定期快照

### 8.4 可扩展性要求

- 插件化架构，新增工种只需添加插件目录
- Prompt 模板可独立更新，无需修改核心代码
- 评分规则可配置，支持工种差异化
- 支持自定义报告模板

### 8.5 兼容性要求

- Node.js ≥ 20
- 现代浏览器（Chrome 90+ / Firefox 90+ / Safari 15+）
- 支持 Windows / macOS / Linux 跨平台运行
